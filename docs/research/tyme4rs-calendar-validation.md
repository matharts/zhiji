# tyme4rs 1.5.1 历法验证

验证日期：2026-11-10。固定发布版 `1.5.1`，使用[独立验证工程与锁文件](../../tools/calendar-validation/README.md)。评估当时尚未接入 App；当前日期换算、真太阳时与干支反推均已通过独立历法包 `zhiji_calendar` 接入，职责见[架构](../architecture.md#日期计算包)。下文保留该次独立验证的范围和结果。

## 结论

保留 `tyme4rs` 作为历法底座候选，但不能根据 `1..=9999` 的参数校验承诺整个范围无条件可用。本轮发现官方历表差异、古代日期的库内往返问题，以及改历月枚举崩溃。接入前需要明确日期口径、可用日期域与错误边界。

评估流程通过表示完整执行比较并保留差异，不表示全部参考值一致或整个范围已具备天文学准确性证明。

## 参考来源

- [香港天文台公农历对照表](https://www.hko.gov.hk/tc/gts/time/conversion.htm)：200 份 1901–2100 年 PDF 的带行号文本快照，重新解析后共 **73,049 天**。检查完整行号、逐日连续性、月长、闰月及跨年顺序。**73,030 天**具有明确或可通过连续关系得到的月份；1901-01-01 至 01-19 的十九天保留未知月份，只核对年和日数，没有用候选库反填期望月份。
- [台湾中央气象署日历资料](https://www.cwa.gov.tw/Data/astronomy/2024cal.pdf)：2018–2027 年 **240 个节气时刻**，公布到分钟，表中标明 UTC+8。部分缓存省略无关 PDF 页，检查要求所用节气表段落行号连续且二十四项完整，不声称归档了整份 PDF。
- 文本快照压缩保存在工具的 `fixtures/reference-extracts.json.gz`；[来源清单](../../tools/calendar-validation/source-manifest.json)固定各组提取文件的字节数与 SHA-256。这是先前的 PDF 文本提取，不是原始 PDF 字节归档。2040 年采用同一官方机构 `www.weather.gov.hk` 的补提取版本。
- 本轮重新打开 HKO 1916、1979、2057 年表及 CWA 2024 年表核对标签和分钟值。解析与比较的负向对照覆盖缺行、错日、错年、错误时刻、空数据、闰月符号错误与缺失输出。

这些检查不能排除所有出版或提取问题。原表差异完整保留，没有通过修改参考值来对齐库。

## 现代日期的独立比较

| 检查 | 实际结果 |
| --- | --- |
| HKO 逐日参考 | 73,049 天，1901-01-01 至 2100-12-31 |
| 与可用参考字段一致 | 73,019 天 |
| 农历日期差异 | 30 天，2057-09-28 至 2057-10-27 |
| 同一输入的库内公→农→公 | 73,049 天均一致 |

**2057-09-28** 的 HKO 日期为九月初一，库为八月三十；库的九月初一为次日，双方在 10 月 28 日重新一致。[HKO 年表](https://www.hko.gov.hk/tc/gts/time/calendar/pdf/files/2057.pdf)、[文字版本](https://www.hko.gov.hk/en/gts/time/calendar/text/files/T2057e.txt)。

HKO 对照表的说明指出，新月或节气接近午夜时，远期日期可能出现一日差异，并明确列出 2057 年这次新月。现有证据确认两种发布结果不同，不能据此裁定哪个远期模型一定正确。本轮没有决定或实现按 HKO 覆盖库结果。

## 节气两条日期路径

HKO 的 **4,800 个节气日期**分开比较：`SolarTerm::get_solar_day()` 的日历日期有 **1 处**差异；`get_julian_day().get_solar_time()` 的精确时刻取日期部分有 **6 处**差异。两条接口不是同一种日历日期承诺。

日历日期的唯一差异为 **1979 大寒**：HKO 为 01-21，库为 01-20；库的精确值为 01-20 23:59:56。该值临近日界，需要独立更细精度资料进一步判断。[HKO 1979 年表](https://www.hko.gov.hk/tc/gts/time/calendar/pdf/files/1979.pdf)。

| 年份 / 节气 | HKO 日期 | 库精确时刻（UTC+8 口径） |
| --- | --- | --- |
| 1912 小雪 | 11-23 | 11-22 23:48:08 |
| 1913 秋分 | 09-24 | 09-23 23:52:41 |
| 1917 大雪 | 12-07 | 12-08 00:00:59 |
| 1927 白露 | 09-08 | 09-09 00:05:25 |
| 1928 夏至 | 06-21 | 06-22 00:06:23 |
| 1979 大寒 | 01-21 | 01-20 23:59:56 |

上表仅列出差异，本轮不推断历史口径差异的成因。

CWA 2018–2027 年 **240 个分钟参考**中，绝对差值超过 30 秒的有 6 项，超过 60 秒的为 0 项；最大值 **36 秒**，为 2025 清明：参考 04-04 20:48，库为 20:48:36。[CWA 2025 年表](https://www.cwa.gov.tw/Data/astronomy/2025cal.pdf)。这是与公布到分钟的值之差，不能解释为已证明计算误差不超过 36 秒，更不能推出秒级准确性。

## 宽范围逐日内部一致性

扫描使用库的混合历制：1582-10-04 后接 10-15，之前按儒略历。当前 App 的 `CivilDate` 使用前推格里高利历，两者需要显式适配。

| 检查 | 实际结果 |
| --- | --- |
| 公历数值范围逐日往返 | 3,652,061 次，含 239,976 个月首/末边界输入 |
| 农历可取得月长的逐日往返 | 3,652,459 次，含 247,368 个月首/末边界输入 |
| 公→农→公不等 | 160 次，位于公历 9、24、25、240 年 |
| 公历转换 panic | 100 次，位于公历 10、13、15、16、18、19、21 年 |
| 农→公→农不等 | 219 次，位于农历 8、23、24、239 年 |
| 农历转换 panic（非首尾越界） | 100 次，位于农历 10、13、15、16、18、19、21 年 |

**579 次问题调用**是两个方向的计数，不等于 579 个互不重叠的真实日期。例如公历 `9-01-01` 转农历再转回会得到 `9-01-31`，足以否定全部数值域必定往返正确的承诺。

另记录以下边界，未混入上表的区间内部问题：

- 农历 `-1` 年十三个月均无法取得月长，会因内部构造 `-2` 年而 panic；这些缺失元数据没有计入成功检查日数。
- 农历首尾越出公历可表示范围的逐日调用有 **339 次 panic**，单独归类。
- 公历 `1-01-01` 对应农历 `0-11-18`；`9999-12-31` 对应农历 `9999-12-02`。不能把农历年界直接等同公历年界。
- `SolarMonth::from_ym(1582,10).get_days()` 尝试构造被跳过的 10-05 并 panic。主扫描按连续日序枚举该月的 21 个实际日期，另保留这次枚举 API 崩溃。
- `SolarDay::new(0,1,1)` 和 `new(10000,1,1)` 都 panic，而非返回 `Err`；接入前仍须检查输入边界。

逐日扫描证明的是已测接口的内部一致性与失败位置，不证明古代实际颁行历法或远期天文精度。`catch_unwind` 仅用于隔离探测，不作为 App 的错误处理方案。

## 接入判断与复跑

现代区间已有独立参考覆盖，但需保留 2057 年模型差异。全数值范围有古代问题日期，不能只凭构造器年界开放无条件取数。日历日期与精确瞬间、前推公历与混合历制、有效日期域与错误反馈均需写入后续接入契约。

真太阳时与干支反推统一由独立历法包 `zhiji_calendar` 的不同模块实现。它们还需各自验证时标、历史时区、日界与搜索范围；本轮不宣称完成这些功能。

从仓库根目录运行工具 [README](../../tools/calendar-validation/README.md) 中的三条命令。结果位于 `target/calendar-validation/`：

- `references/`：重新解析的逐日和节气数据、逐份来源 URL 与内容哈希。
- `results/calendar-differences.json`：全部现代逐日差异与往返问题。
- `results/term-calendar-date-differences.json`、`term-instant-date-differences.json`：两条节气路径的完整差异。
- `results/term-minute-comparison.json`：全部分钟参考比较。
- `results/boundaries-actual.json`、`summary.json`：逐日计数、问题调用、端点和边界分类。

验证工程包含格式、严格 Clippy、Rust 回归与 Node 解析/比较负向对照；App 日期计算接口、现有排盘引擎及生产依赖未在本轮改动。
