# 代码开发规范

本文约束项目中的 Rust 实现。模块职责和状态所有权见[架构](architecture.md)，测试与性能验证见[测试约定](testing.md)。

## 类型与接口

- 用类型表达有效状态和取值范围；需要区分取消、失败、冲突和完成时使用不同状态，不以空值或布尔值混合表示。
- 按模块职责收拢数据和行为；默认私有，仅在实际跨模块协作时扩大可见性。跨层传递稳定的数据或操作，不暴露可随意修改的内部状态。
- 不完整的手动排盘输入是正常状态。处理领域输入时遵循[领域规则](domain.md)，不以 `unwrap` 将用户可触发的未选择状态变成崩溃。
- 先使用现有标准库和项目依赖；引入依赖应说明用途、维护成本、许可和平台影响，并更新锁文件。可选开发工具不应成为应用运行依赖。

## 错误与外部输入

- 文件、系统对话框、剪贴板和后台任务可能取消、失败或中断。保留可辨认的结果，并将错误反馈给对应操作；不要将取消显示为成功或错误。
- 读取草稿等外部数据时，在替换当前状态前完成格式、范围和资源限制校验。失败时保留当前会话。
- 错误信息在界面上说明操作结果和可采取的下一步；诊断记录保留必要的操作阶段与底层原因，但不记录草稿全文或其他无关用户数据。
- `unwrap` / `expect` 适用于测试和有明确不变量的内部场景；对可能失败的系统调用、外部输入和用户操作应显式处理错误。说明无法从上下文判断的前提。

## 任务与资源

- UI 线程处理交互与状态提交；耗时文件、编码和渲染工作按现有任务边界执行。后台任务只接收所需的快照、通道与唤醒能力。
- 异步操作在发起时确定输入；完成时只提交仍属于该操作的结果。处理任务取消、发送端断开、线程启动失败及关闭期间的状态，不依赖任务一定成功返回。
- 文件写入保留现有临时文件、冲突确认和清理语义。更改提交方式时检查失败及并发创建目标的情况；不能以静默覆盖简化流程。
- 仅在安全 Rust 或现有封装无法完成平台集成时使用 `unsafe`。缩小作用域，并在代码旁说明指针或句柄有效性、线程要求、所有权和生命周期；平台代码通过条件编译限定范围。

## 修改质量

- 优先修改拥有该行为的模块；删除被替代的路径，避免添加平行状态或只转发一次的抽象。
- 代码和方法使用中文注释，说明职责、约束、不可推导的原因或安全前提；不逐行复述代码。公开接口的说明应帮助调用者理解前置条件和失败方式；新增或修改代码时同步维护注释。
- 将行为变化、依赖升级和结构重构保持在可审查的范围。对外可观察行为改变时，在变更说明中写出触发条件、结果与验证范围。
