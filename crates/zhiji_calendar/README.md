# zhiji_calendar

独立 Rust 历法包，提供受校验的基础类型、固定 `tyme4rs 1.5.1` 的公农历转换适配、IANA 时区解析、真太阳时近似计算及干支反推。桌面 App 调用该包；包不依赖桌面应用、Rune、`zhiji_ui` 或 `zhiji_core`。

```rust
use zhiji_calendar::{Calendar, CivilCalendar, SolarDate};

let date = SolarDate::new(2023, 3, 22, CivilCalendar::ProlepticGregorian)?;
let lunar = Calendar.to_lunar(date)?;
assert!(lunar.month().is_leap());
assert_eq!(Calendar.to_solar(lunar, date.calendar())?, date);
# Ok::<(), zhiji_calendar::Error>(())
```

## 日期与数值范围

- `SolarDate` 的数值年为 1–9999。构造时必须显式选择 `ProlepticGregorian`（与 App 现有公历选择器一致的前推格里高利历）或 `GregorianReform1582`（1582-10-04 后接 10-15，此前使用儒略历）。日序相同的日期可投影为不同历制标签。
- 前推格里高利历的日序换算由 `time::Date` 提供；库的类型留在实现内部，公开接口不暴露第三方日期类型。
- `LunarDate` 的数值年为 0–9999；零年用于表达最低公历端点所对应的农历日期。月份由 `LunarMonth` 的数字和闰月标志共同表示。
- `SolarDate::new` 校验民用日期结构；`LunarDate::new` 还检查实际闰月和月长。合法民用日期不保证位于后端可转换域。

数值范围不是连续可用域，也不是独立准确性保证：

- 适配层保守拒绝 8–25 年、239–240 年的历史异常区间。检查同时作用于转换需要的后端日期与农历元数据，因而邻近公历年也可能返回不支持。
- 历史月长不属于 29/30 日模型时返回 `NonStandardLunarMonth`；例如农历 236 年十二月。它与已知历史区间拒绝分别报告。
- 农历端点可能超出后端公历范围；前推格里高利历的输出还须处于公元 1–9999 年。越界返回 `ConversionEndpoint`，不会将日期夹紧到端点。
- 每次转换核对日序或反向年月日；不一致返回 `BackendInconsistent`。已知不安全输入在调用相关后端接口前被拒绝，不使用 `catch_unwind` 恢复计算。
- 保留固定后端的计算结果，包括 2057 年与 HKO 的已记录差异，不自动覆盖为官方年表。范围证据与准确性限制见[验证报告](../../docs/research/tyme4rs-calendar-validation.md)。

## 其他基础类型

`TimeOfDay` 使用时、分、秒，不接受闰秒标签；`CivilDateTime` 是民用钟表字段，不表示已经解析的唯一时刻。`Longitude` 使用向东为正的角度，范围 -180° 至 180°，拒绝 NaN 和无穷值，0° 是有效经度。`UtcOffset` 以秒保存明确偏移，保留历史偏移中的秒数，不根据经度猜测时区或解析夏令时。

`DayBoundary` 表达调用方需要明确选择的日界规则，不设置公共默认值。紫微取数与四柱反推的分界规则分别处理。

## 真太阳时

`resolve_local_time` 使用内嵌的 `chrono-tz 0.10.4` / IANA 2025b 数据，将地点时区与钟表时间解析为唯一、重复或不存在的时刻。重复结果保留较早和较晚两个 UTC 时刻，不替调用方选择；不存在的钟表时间不自动挪到下一时刻。历史记录尤其是 1970 年以前的数据，不能代表每个地区完整、准确的实际用时历史；未来规则也是数据库的预测，不读取机器当前时区。

`apparent_solar_time` 接收出生地钟表时间、东经为正的经度和该时刻的实际 UTC 偏移，返回原始时间、近似真太阳时、均时差与总修正量。调用方先解析当地时区与夏令时；偏移含夏令时，不由经度推断。0° 是有效经度。输出时刻按秒四舍五入，并保留跨日结果与输入历制。

均时差按[美国海军天文台太阳坐标近似算法](https://aa.usno.navy.mil/faq/sun_approx)计算，关系采用[NOAA 真太阳时公式](https://gml.noaa.gov/grad/solcalc/solareqns.PDF)。仅接受 UTC 1800-01-01 至 2200-12-31 的时刻，超出返回 `SolarModelRange`；此范围与公农历数值范围不同。模型将 UTC 近似为 UT1，不处理闰秒，也不提供历史时标或时区数据库。USNO 对该范围内太阳坐标给出约 1 角分的近似说明，这不是此实现的秒级误差保证。跨日、时辰和其他分界附近，近似误差可能影响结果，不应当作精确边界判断。

测试中一个 NREL SPA 算例的均时差参考值用于独立抽样对照；该抽样不证明整个范围内的准确性。

## 四柱与干支反推

`four_pillars` 正算，`reverse_four_pillars` 搜索包含起止年的完整区间；`Ganzhi` 的 0–59 分别表示甲子至癸亥。输入和输出使用前推格里高利历，时间字段按 UTC+8 的固定钟表刻度解释，与 `tyme4rs` 节气时刻处于同一刻度；这不是按地点解析的历史时区，也不自动将真太阳时与节气时刻互相换算。

年柱、月柱分别在立春及十二节的交接时刻切换。日柱支持 0 点和 23 点换日，调用方必须明确选择。晚子时可明确选择时干跟随日柱或按次日日干；App 已采用按次日日干，日柱默认在 0 点换日，可在设置中改为 23 点。候选以包含起点、不包含终点的秒级时间区间返回；节气发生在时辰内部时会切分区间。搜索检查区间的首末秒，不依赖 `tyme4rs` 的内置反查接口。

上述固定刻度接口的数值搜索范围为公历 4–9997 年；这一范围仅表示算法可处理的输入，不保证远古或远未来的节气和干支具有经独立验证的准确性。

`four_pillars_for_birth` 接收已解析的出生时刻和经度。年柱、月柱用同一真实时刻的 UTC+8 投影比较节气；日柱、时柱使用该时刻在出生地的真太阳时，避免拿真太阳时钟表字段直接与北京时间节气字段比较。

`reverse_birth_pillars` 接收地点时区和经度，在当地公历完整年份内搜索，范围为 1801–2199 年，保留模型端点余量。反推先在真太阳时刻度定位时辰区间，再回到真实 UTC 秒逐一复核四柱；候选保留 UTC 区间、当地钟表区间和实际偏移，并在偏移变化、当地或真太阳时跨日处拆分。重复钟表时间不会合并。区间含起点、不含终点。

`reverse_birth_pillars_cancellable` 使用相同规则，额外接受返回布尔值的取消检查。首次计算前、每日筛选及逐秒复核之间会调用该检查；返回真时以 `Error::Cancelled` 结束，不返回部分候选。调用方负责线程和取消信号的所有权；该接口不依赖运行时，不改变原有不可取消接口的结果。

秒级区间是库计算结果的分辨率，并非秒级天文准确度；已比较的节气及误差见[历法验证](../../docs/research/tyme4rs-calendar-validation.md)。UTC 仍按模型近似为 UT1，未引入完整 TT/UT1、历史地球自转或闰秒服务；靠近时辰、日界和节气交接时应考虑模型误差。
